# تنفيذ قاعدة البيانات — المرحلة الثانية

## حالة مساحة العمل

تم العثور على `docs/ERD-Review.md` داخل مساحة عمل `Hamak-Node-Workspace`، لكن هذه المساحة لا تحتوي على بيانات Git أو ملفات مصدر أخرى للفريق. لذلك لا يمكن التحقق من أنها المستودع الرسمي. مجلدا `backend` و`database` كانا فارغين قبل إضافة ملفات هذه المرحلة. لا يوجد إعداد Prisma سابق، ولا متغير اتصال `DATABASE_URL`، ولا `psql` أو Docker متاحان في البيئة.

## ما نُفّذ

- أُنشئت وحدة Prisma مستقلة في `database` لتجنب تغيير إعدادات التطبيق أو الملفات السابقة.
- أُضيف نموذج `Component` وارتباط `InventoryMovement` به بمفتاح أجنبي يمنع حذف المكون ذي الحركات.
- أُضيفت جداول `users`, `sessions`, `teams`, `requests`, `request_items`, `deliveries`, `delivery_items`, `returns`, `return_items`, `inventory_movements`, `audit_logs`, و`hackathon_summaries`، مع مفاتيح أجنبية مقيدة وفهارس تاريخ/بحث. جدول `teams` وتقسيم التسليم إلى رأس وبنود اختياران موصى بهما في مراجعة ERD، لا حسم رسمي لهما.
- أُضيفت قيود عدم سلبية الأرصدة، وصحة كميات الطلب/الاعتماد والتسليم والإرجاع، وانتهاء الجلسة بعد إنشائها، وربط بند التسليم بالطلب نفسه في الرأس وبند الطلب.
- يفرض فهرس فريد جزئي طلب `PENDING` واحداً لكل فريق للطلبات المرسلة. يبقى نص الحالات حراً، ولا توجد قائمة enum مفترضة.
- لا يمكن إضافة بنود الطلب إلا قبل الإرسال؛ بعده تثبت بيانات الطلب وبنوده، ويسمح بتغيير كمية الاعتماد فقط أثناء `PENDING` وبما لا يقل عن الكمية المسلّمة. أُضيفت `submitRequest` لإنشاء الرأس والبنود ثم الإرسال في معاملة واحدة.
- تُسجل كل حركة مخزون في سجل إلحاقي وتغيّر رصيد المكون في trigger ضمن المعاملة نفسها. تُنشئ بنود التسليم/الإرجاع حركاتها آلياً؛ تحرس triggers حدود الاعتماد والعهدة مع قفل صف البند ذي الصلة للتزامن.
- أُضيفت طبقة تدقيق إلحاقية ترفض بيانات JSON التي تحتوي مفاتيح حساسة شائعة (كلمة مرور/رمز/سر/ملف تعريف ارتباط/تفويض). أُضيفت أيضاً خدمة حفظ لقطة JSON مستقلة وملحقية للهاكاثون، دون تنفيذ Reset.
- أُضيفت تقارير الأرصدة المسجلة، تفاصيل الحركات وتجميع صافيها حسب النوع/الحالة، عدد الطلبات حسب الحالة، العهد المفتوحة، ولوحة إحصاءات تجمع هذه المقاييس.
- أضيفت بيانات اصطناعية مترابطة للمخزون والحساب والفريق والطلب والتسليم والإرجاع والحركة والتدقيق والملخص. لا تحذف أو تحدّث سجلات؛ وتتخطى seed إذا وجدت مكون التعريف التجريبي.
- لا تحتوي ملفات الإعداد على بيانات اعتماد فعلية؛ `database/.env.example` يستخدم قيمًا توضيحية فقط.
- Prisma `7.10.1` مع PostgreSQL adapter. يتطلب Prisma Node.js `20.19+` أو `22.12+` أو `24.x`; إصدار النظام `26.13.0` غير مدعوم. أضيف حارس يمنع أوامر Prisma على إصدار غير مدعوم. تحقق المخطط وتوليد العميل نفذا فعلياً باستخدام Node.js `24.22.2` مؤقت عبر npm، دون تغيير تثبيت Node في النظام.

## ما لم يُنفّذ ولماذا

الحسابات ممثلة بسجل مستخدم محايد (نوع حساب نصي اختياري بلا enum أو ربط مفترض للفريق)، ولم ينشأ جدول `roles` أو عضوية فرق. جدول الفريق المستقل اختير كتمثيل موصى به لهوية الفريق اللازمة للعلاقات وقيد الطلب المعلق؛ يجب اعتماد هذا الاختيار أو تغييره قبل نشر migration. كذلك جداول `deliveries` و`delivery_items` تمثيل مقترح موصى به للتسليم الجزئي ويحتاج تأكيد الكوتش.

يظل `account_type` و`status` و`movement_type` نصوصاً غير مقيدة حتى اعتماد قيمها. قُيد `quantity_bucket` فقط إلى `working`/`broken` لأن الفصل مؤكد في الخطة. لم يفرض المخطط حداً للجلسة النشطة بسبب عدم تعريف الحساب/نشاط الجلسة، ولم يفرض الأدوار أو البريد/SKU الفريدين. لا توجد آلية حجز مخزون عند القبول أو ضمان كفاية المخزون وقت الاعتماد بعد؛ حالة الموافقة التي تفعّل الحجز وقواعد الرفض/التحرير لم تحسم. التحقق الذري من التسليم والإرجاع مطبق.

لم تضاف الصور لأن عددها وطريقة تخزينها غير محددين. تقرير المخزون يوضح الأرصدة العاملة والمعطوبة المسجلة؛ لا يسمي مجموعهما إجمالي الملكية ولا يحسب المحجوز أو العهدة ضمن رصيد المتاح.

تخزن الملخصات كـ JSONB مستقل وإلحاقي، لكن محتواها الرسمي/فترتها/شكلها لم يعتمد. لا توجد آلية Reset أو شروط تنفيذها، ولا جداول مالية للمستحقات؛ لم يُنفذ أو يُفترض حذف أو تصفير لأي بيانات.

الحالات `APPROVED` المستخدمة في بيانات seed والاختبار مثال نصي غير مقيد فقط، وليست اعتماداً لاسم الحالة الرسمية. يعمل فهرس الطلب المعلق على القيمة المؤكدة `PENDING`.

## التحقق

نجح `prisma validate` و`prisma generate` على Node.js `24.22.2`. نجحت اختبارات PGlite المحلية: **16/16** (قيود SQL والعلاقات والحركات والتسليم والإرجاع والتدقيق/الملخصات، إضافة إلى التقارير والخدمات). شغّل `npm audit` بلا تحذيرات معروفة في التبعيات. يرفض `npm run db:validate` إصدار Node النظام الحالي `26.13.0` برسالة متعمدة؛ لا يعد هذا فشل تحقق للمخطط. لم يطبق migration على خدمة PostgreSQL فعلية ولم يشغّل seed بسبب غياب `DATABASE_URL` وخادم Postgres. لم يُختبر ضغط تنافس متزامن فعلياً؛ حراسة التزامن موجودة في triggers لكنها تحتاج اختباراً إضافياً على PostgreSQL. يلزم اختبار نشر نهائي على نسخة PostgreSQL المستهدفة، إذ PGlite محرك مضمّن وليس خدمة الإنتاج.

الترحيل الإضافي مولد بمقارنة Prisma إلى baseline محفوظ في `database/prisma/baselines/20261031190000_initial.prisma`، ثم أضيفت إليه triggers وقيود `CHECK` غير ممثلة مباشرة في Prisma Schema. شُغّل SQL الترحيلين كاملين في اختبار PGlite.

## 2. ما أضيف لإكمال الربط (دون تغيير الجداول أو العلاقات)

لم يُضف أي جدول أو عمود. الإضافات كلها مسارات API وردت في الخطة ولم تكن منفّذة، أو تكييف للنشر:

- `GET /api/team/custody` — العهدة المجمّعة للفريق (الخطة §09).
- `GET/POST /api/admin/users`, `PATCH /status`, `POST /reset-password`, `POST /sessions/revoke` — إدارة الحسابات والجلسات (الخطة §02، §09).
- `GET /api/admin/components` — عرض الأدمن لكل القطع بما فيها المعطلة مع المحجوز/المتاح/بعهدة الفرق.
- `GET /api/admin/dashboard`, `GET /api/admin/reports/movements`, `GET /api/admin/hackathon-summaries`.
- `POST /api/admin/reset-hackathon-data` (+ `/check`).
- `POST /api/chat/messages`, `GET /api/chat/inventory-search`, `GET /api/chat/status` — المساعد التقني بأدوات قراءة فقط.
- `DELETE /api/components/:id` أصبح يحذف نهائياً فقط إذا لم يكن للقطعة أي سجل، وإلا يعطّلها (الخطة §02).
- `PATCH /api/components/:id` يمنع جعل العامل أقل من المحجوز (الخطة §05)، ويقبل اختيار صورة جاهزة.
- تفاصيل الطلب تُرجع الآن المسلّم والمعاد (سليم/عاطل) والعهدة وحالة الإرجاع لكل بند.
- ترحيل `20261116090000_component_images`: يملأ `image_reference` لكل قطعة مستوردة (بيانات فقط).
- ترحيل `20261116091000_enable_row_level_security`: يفعّل RLS لمنع الوصول المباشر عبر Data API الخاص بـ Supabase.

## 3. تكييفات النشر (Vercel + Supabase)

- الخادم يعمل كـ Serverless Function واحدة (`api/index.js`) على نفس النطاق مع الواجهة ⇒ لا مشاكل CORS أو Cookies بين نطاقين.
- قرص Vercel للقراءة فقط ⇒ الصور المرفوعة تذهب إلى Supabase Storage ويُحفظ الرابط فقط في القاعدة (كما تنص الخطة). المتصفح يحوّل أي صورة إلى WEBP ويصغّرها قبل الرفع، فبقيت قاعدة الخادم "WEBP فقط".
- اتصال PostgreSQL عبر Transaction Pooler مع مجمّع اتصالات صغير، وTLS مع Supabase.
- حماية CSRF: تُقبل الطلبات المعدِّلة فقط إذا كان `Origin` هو نفس نطاق الموقع أو `FRONTEND_URL`.
- حساب الأدمن الأول عبر متغيرات `BOOTSTRAP_ADMIN_*` (تعمل مرة واحدة فقط عند عدم وجود أي أدمن).

## 4. فروقات بين واجهة لجين التجريبية وقواعد الخطة (طُبّقت قواعد الخطة)

| واجهة لجين التجريبية | المطبّق الآن |
|---|---|
| "طلب معتمد واحد فقط للفريق" | طلب *قيد المراجعة* واحد فقط؛ بعد القبول/الرفض يمكن طلب جديد (الخطة §02) |
| الفريق يطلب "إعادة القطع" والمشرف يؤكد | المشرف يسجّل الإرجاع (جزئي/كامل، سليم/عاطل) عند الاستلام (الخطة §03) |
| خصم الكمية عند إرسال الطلب | لا حجز عند الإرسال؛ الحجز عند القبول والخصم عند التسليم (الخطة §05) |
| الدخول بالبريد وتحديد الدور من البريد | اسم مستخدم + كلمة مرور، والدور من الخادم |
| أسماء الأعضاء حقل مستقل | تُضاف أسماء الأعضاء إلى شرح المشروع (لا يوجد عمود لها في الـ ERD) |

## 5. نقاط تحتاج قراراً من الفريق لاحقاً

- **التصفير:** قاعدة طارق تمنع حذف الطلبات والتسليمات والإرجاعات (Triggers "سجل تاريخي")، بينما الخطة تذكر حذف الطلبات. لاحترام تصميم القاعدة، التصفير **يؤرشف**: يعطّل حسابات وفرق الهاكاثون ويُخفي بياناتها ويحرّر أسماء المستخدمين ويحفظ الملخص النهائي. إذا أراد النادي حذفاً فيزيائياً يلزم ترحيل يعدّل الـ Triggers.
- **إلغاء الكمية المتبقية غير المسلّمة:** القاعدة تمنع تغيير الكمية المعتمدة بعد خروج الطلب من حالة Pending، لذلك هذه العملية غير متاحة حالياً (تحتاج عموداً/ترحيلاً — خارج نطاق "عدم تغيير التصميم").
- **حفظ سجل المحادثات:** اختياري في الخطة؛ المساعد حالياً لا يحفظ المحادثات (لا جداول `chat_*`).
- محدّد محاولات الدخول يعمل داخل كل نسخة Serverless (كما ورد في ملاحظات الخادم الأصلية).

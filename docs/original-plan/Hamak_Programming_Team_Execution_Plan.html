01 — الهدف وطريقة بناء النظام

المنصة مخصصة لإدارة مخزون القطع الإلكترونية، وطلبات الفرق، والعهدة والتسليم والإرجاع، مع مساعد تقني موجّه للهاكاثون يقدم استشارات تقنية ويبحث في المخزون الفعلي ويقترح القطع المناسبة للأفكار.

واجهة الفريق

تسجيل الدخول، تصفح القطع العاملة وصورها وكمياتها المتاحة، إنشاء طلب يحتوي اسم المشروع وشرحه والقطع المطلوبة، متابعة الطلب والعهدة، واستخدام المساعد التقني.

واجهة الأدمن

إدارة المخزون والصور والكميات، مراجعة الطلبات، تسجيل التسليم والإرجاع، إدارة الحسابات، متابعة التقارير وسجل التدقيق، وتصفير بيانات الهاكاثون بشروط صارمة.

Backend

المكان المركزي للمصادقة والصلاحيات وقواعد العمل وحساب الكميات وإدارة الطلبات وتوفير واجهات API.

AI Chatbot

مساعد تقني محدود النطاق، يستخدم أدوات قراءة محدودة لاسترجاع معلومات المخزون الحقيقية بدلاً من تخمينها.

مبدأ معماري: النظام واحد، والواجهة لا تتصل بقاعدة البيانات مباشرة. تمر البيانات عبر Backend يتحقق من الصلاحيات ويطبق قواعد العمل، والمساعد لا يملك صلاحيات إدارية.

02 — هيكل الفريق والمسؤوليات

المسارالأعضاءالمسؤولية الأساسية
إدارة المشروع والتكاملمالكالأولويات والمهام، المعمارية والتكامل، المصادقة والصلاحيات ودورة حياة الطلبات ومراجعة جاهزية الإصدار.
Frontendلجين، محمدواجهات الفريق والأدمن والمحادثة وربطها بواجهات API.
Backendمالك، بتول، طارقالخادم وقواعد العمل وواجهات API والتكامل مع قاعدة البيانات.
AIشهد، نهادسلوك المساعد، نطاق الإجابات، أدوات البحث في المخزون وتقييم التوصيات.
تنظيم المسؤولية: مالك مسؤول عن المعمارية والتكامل، لكنه ليس نقطة مرور إلزامية لكل قرار يومي. لكل مسار مسؤول واضح، وتوثّق القرارات المؤثرة على النظام كله.

مالك — المعمارية والمصادقة

  • إعداد Express وبنية الخادم ومعالجة الأخطاء.
  • تسجيل الدخول والخروج والتحقق من كلمات المرور.
  • التحقق من دور admin أو user لكل مسار محمي.
  • إدارة الجلسات: جلسة نشطة واحدة لحساب الفريق، مع السماح للأدمن بعدة جلسات.
  • إنشاء الطلبات والتحقق من اسم المشروع وشرحه وبنوده.
  • قواعد قبول الطلب وحجز الكميات وحالات الطلبات.
  • مراجعة التكامل وPull Requests.

بتول — المخزون والتسليم والإرجاع

  • API كتالوج القطع العاملة وصورها والكميات المتاحة.
  • إضافة القطع وتعديلها ورفع الصور والتحقق من الملفات.
  • قواعد تعديل المخزون وتعطيل القطع أو حذفها بشروط.
  • تسجيل التسليم والإرجاع الجزئيين.
  • تمييز الكميات المعادة سليمة أو عاطلة.
  • تسجيل حركات المخزون واختبار منع تجاوز الكميات.

طارق — قاعدة البيانات والتقارير

  • مراجعة ERD والجداول والعلاقات والمفاتيح الخارجية.
  • إنشاء مخطط Prisma والترحيلات.
  • القيود وبيانات Seed التجريبية.
  • تنسيق سجلات حركات المخزون والتدقيق.
  • التقارير والإحصائيات.
  • حفظ ملخصات الهاكاثون قبل تصفير بيانات الفرق والطلبات.

لجين — واجهة الفريق

  • واجهة تسجيل الدخول وحساب الفريق.
  • كتالوج القطع وصورها والكميات المتاحة.
  • نموذج الطلب: اسم المشروع وشرحه والقطع والكميات.
  • تأكيد الإرسال والتنبيه إلى عدم إمكانية تعديل الطلب بعد إرساله.
  • متابعة الطلبات وإلغاء الطلب عندما يكون مسموحاً.
  • صفحة العهدة المجمعة عبر طلبات الفريق.
  • المساهمة في واجهة المحادثة عند الحاجة.

محمد — واجهة الأدمن

  • لوحة الأدمن وملخص المخزون والطلبات.
  • إدارة القطع والصور والكميات.
  • مراجعة الطلبات وعرض معلومات المشروع والقطع.
  • واجهات التسليم والإرجاع الجزئي.
  • إدارة الحسابات والتقارير.
  • واجهة تصفير البيانات مع التحذير والتأكيد والشروط.

شهد — سلوك المساعد

  • تعريف نطاق المساعد ضمن الهاكاثون والمشاريع التقنية.
  • صياغة تعليمات النظام (System Instructions).
  • اقتراح أفكار مشاريع وتطويرها مع المستخدم.
  • معالجة الأسئلة الخارجة عن النطاق برسالة توجيه.
  • إعداد مجموعة أسئلة لتقييم جودة الإجابات.

نهاد — أدوات المخزون والتوصية

  • تحديد بيانات القطع اللازمة للتوصية.
  • تصميم أدوات قراءة محدودة للبحث في المخزون.
  • التنسيق مع بتول حول بيانات القطع والكميات المتاحة.
  • مطابقة فكرة المشروع مع القطع الموجودة.
  • منع اختلاق أسماء القطع والكميات واختبار الحالات المختلفة.

04 — تأسيس GitHub والفروع

  1. تأكدوا من رابط المستودع ومالكيه وصلاحياته.
  2. أضيفوا أعضاء الفريق بصلاحيات تسمح بإنشاء الفروع ورفعها وفتح Pull Requests.
  3. فعّلوا حماية الفرع المستقر main لمنع التعديل المباشر متى كانت إعدادات المستودع تسمح بذلك.
  4. جهّزوا README.md و.gitignore و.env.example والوثائق الأولية.

05 — دورة العمل اليومية باستخدام Git

مثال: محمد يعمل على واجهة إدارة المخزون.

1. تحديث develop

git switch develop
git pull origin develop

2. إنشاء فرع

git switch -c feature/inventory-management

3. فحص التغييرات

git status
git diff

4. حفظ Commit

git add frontend/
git commit -m "feat(frontend): add inventory management UI"

5. رفع الفرع

git push -u origin feature/inventory-management

6. فتح Pull Request

يفتح محمد PR من feature/inventory-management إلى develop ويشرح ما أضافه وكيف اختبره، ويذكر أي اعتماد على API غير جاهز.

7. المراجعة والدمج

يراجع عضو آخر التغيير ويتأكد من نجاح الاختبارات وعدم كسر أجزاء موجودة. لا تعتبر المهمة منتهية بمجرد رفع الفرع.

Merge Conflict: تعارض تغييرات يتطلب مراجعة يدوية عند تداخل تعديلات الأعضاء. لا تختاروا نسخة أحدهم عشوائياً. قللوا التعارض بتقسيم الواجهات إلى ملفات مستقلة والاتفاق على الملفات المشتركة مسبقاً.

06 — عقد API: الاتفاق الذي يربط الفرق

قبل تنفيذ الميزة نفسها في الواجهة والخادم، اتفقوا على المسار ونوع الطلب والبيانات والصلاحيات والاستجابة والأخطاء. يمكن لكل فريق العمل بالتوازي باستخدام بيانات تجريبية مطابقة للعقد.

العنصرما يجب توثيقه
MethodGET أو POST أو PATCH أو DELETE.
Pathعنوان المسار، مثل /api/components.
Authenticationهل يتطلب تسجيل الدخول؟
Authorizationهل يسمح به لحساب فريق أم للأدمن فقط؟
Requestالبيانات المرسلة والحقول المطلوبة.
Responseشكل البيانات المستقبلة.
Errorsالأخطاء المتوقعة وأكواد HTTP.

مثال: عرض القطع

GET /api/components

{
  "items": [
    {
      "id": "component-123",
      "name": "ESP32 DevKit",
      "imageUrl": "/images/esp32.jpg",
      "availableQuantity": 8
    }
  ]
}

توثّق المسارات في docs/api-contract.md، وتُحدّث الوثيقة كلما تغير العقد المتفق عليه.

المرحلة 1: المصادقة والصلاحيات

  • مالك: تسجيل الدخول والجلسات والصلاحيات.
  • طارق: جداول المستخدمين والجلسات.
  • لجين: واجهة تسجيل الدخول وواجهة الفريق.
  • محمد: الهيكل الأولي للوحة الأدمن.
  • شهد ونهاد: تصميم المساعد دون دمج النموذج بعد.

معيار الإنجاز: يدخل الفريق إلى واجهته والأدمن إلى لوحته، ويرفض الخادم API غير المصرح بها، وتُطبق قاعدة الجلسة النشطة الواحدة للفريق.

المرحلة 2: كتالوج المخزون

  • بتول: API المخزون والإضافة والتعديل والصور.
  • طارق: الجداول والترحيلات والقيود.
  • لجين: كتالوج الفريق.
  • محمد: إدارة المخزون.
  • مالك: مراجعة الصلاحيات والتكامل.
  • نهاد: تحديد بيانات المخزون اللازمة للمساعد.

معيار الإنجاز: إضافة قطعة بصورتها وتعديلها وفق القواعد، وإظهار القطع العاملة والكميات المتاحة للمستخدم، ومنع تعديل يتعارض مع الحجز.

المرحلة 3: الطلبات والمشاريع

  • مالك: API الطلبات وقواعد العمل.
  • طارق: مخطط الطلب وبنوده والقيود.
  • لجين: نموذج الطلب ومتابعة الحالة.
  • محمد: واجهة مراجعة الطلبات.
  • بتول: بيانات المخزون للتحقق.

معيار الإنجاز: يحتوي كل طلب على اسم المشروع وشرحه الخاص به وعدة أنواع من القطع؛ لا يعدّل بعد الإرسال؛ طلب Pending واحد كحد أقصى لكل فريق؛ يمكن إلغاؤه قبل المراجعة؛ ولا يتم الحجز عند الإرسال.

المرحلة 4: القبول والحجز والتسليم والإرجاع

  • مالك: القبول والحجز وتغيير الحالات.
  • بتول: التسليم والإرجاع الجزئي.
  • طارق: السجلات والقيود والتقارير.
  • لجين: الطلبات والعهدة.
  • محمد: واجهات المراجعة والتسليم والإرجاع.

معيار الإنجاز: القبول يحجز الكميات؛ الرفض يحرر الحجز؛ التسليم الفعلي يخصم المخزون؛ التسليم والإرجاع الجزئيان مدعومان؛ وتُسجل القطع المعادة سليمة أو عاطلة.

المرحلة 5: المساعد التقني

  • شهد: تعليمات النظام والنطاق وتوليد الأفكار.
  • نهاد: أدوات البحث وتنسيق بيانات التوصية.
  • مالك: مراجعة التكامل والصلاحيات.
  • بتول: خدمة حساب المتاح.
  • لجين: واجهة المحادثة.
  • محمد: عرض القطع المقترحة بصورها.

معيار الإنجاز: استشارات ضمن النطاق، أفكار مشاريع، بحث فعلي في المخزون، عدم اختلاق قطع أو كميات، وعدم وجود صلاحيات تعديل أو اعتماد.

المرحلة 6: التقارير وتصفير البيانات

  • طارق: التقارير وحفظ الملخصات.
  • مالك: شروط التصفير والصلاحيات.
  • بتول: مراجعة الكميات والحركات النهائية.
  • محمد: واجهة التقارير والتصفير.
  • لجين: التأكد من عدم ظهور بيانات الفرق بعد التصفير.

معيار الإنجاز: لا يتم التصفير مع عهد مفتوحة أو مستحقات غير مسوّاة؛ يتطلب صلاحية أدمن وتأكيداً صريحاً؛ تحفظ إحصائيات القطع المعادة سليمة وعاطلة؛ وتبقى بيانات المخزون وصوره وإحصائياته. تختبر العملية على قاعدة تجريبية أولاً.

11 — إدارة التاسكات عبر GitHub

Issue لكل مهمة

مثال: بناء API إضافة قطعة إلى المخزون.

  • Assignee: بتول.
  • Labels: backend، inventory، P0.

  6. بناء واجهة عرض القطع.

12 — الاجتماعات والتواصل

اجتماع تخطيط أسبوعي

  • ما الذي أُنجز؟
  • ما الذي سينجز الأسبوع القادم؟
  • ما العوائق؟
  • ما الميزات التي تعتمد على بعضها؟

اجتماع تقني عند الحاجة

مثل اجتماع بتول ومحمد لتثبيت عقد API المخزون، أو نهاد وبتول لتحديد بيانات التوصيات.

تحديث المهام

حدّثوا الحالة عند بدء العمل، أو فتح PR، أو انتظار المراجعة، أو الدمج، أو ظهور عائق.

توثيق القرارات

أي قرار يؤثر في المعمارية أو API أو قاعدة البيانات يوثّق داخل المستودع، ولا يبقى في الدردشة فقط.

13 — قواعد تقنية مشتركة

  1. لا أسرار في GitHub: لا ترفعوا ملفات .env الحقيقية أو كلمات المرور أو مفاتيح API. ارفعوا .env.example بأسماء المتغيرات فقط.
  2. لا تعديل مباشر على main: كل ميزة تمر بفروع وPull Requests ومراجعة.
  3. مصدر موحد لقاعدة البيانات: مخطط Prisma والترحيلات مرجع الفريق.
  4. الخادم مسؤول عن الصلاحيات: إخفاء صفحة الأدمن لا يمنع استدعاء API مباشرة.
  5. التعامل مع التزامن: إذا حاول فريقان حجز آخر قطعتين، يجب ألا يتجاوز الحجز المخزون؛ استخدموا معاملات قاعدة بيانات وعمليات تحقق مناسبة.
  6. صلاحيات Chatbot محدودة: أدوات قراءة للمخزون فقط؛ لا حذف ولا تعديل ولا اعتماد طلبات.
  7. كل ميزة لها اختبارات: نجاح السيناريو، مدخلات خاطئة، صلاحيات، حالات حدودية وتكامل.
  8. المخزون لا يُحسب في الواجهة: الحساب النهائي للكميات المتاحة والمحجوزة يتم في Backend.

15 — قائمة تحقق لمدير المشروع

  • تثبيت المستودع الأساسي وهيكله والفروع والصلاحيات.
  • تثبيت قواعد حالات الطلب والحجز والتسليم والإرجاع والتصفير.
  • مراجعة ERD واعتماد الجداول والعلاقات قبل الترحيلات.
  • اعتماد API Contract حتى يعمل Frontend وBackend بالتوازي.
  • إنشاء Issues مرتبة حسب الأولوية، مع مسؤول ومعايير قبول.
  • تدريب الأعضاء على Branch وCommit وPush وPull Request.
  • تنفيذ أول ميزة متكاملة: كتالوج المخزون.
  • مراجعة الاختبارات قبل الدمج إلى develop.
  • التأكد من عدم وجود مفاتيح سرية أو بيانات حقيقية في المستودع.
  • تحديد سياسة حفظ محادثات Chatbot قبل التنفيذ.
  • اختبار تصفير البيانات على قاعدة تجريبية قبل اعتماد العملية.
أهم توصية: لا تبدأوا جميع الميزات دفعة واحدة. ثبّتوا طريقة العمل، ثم أنجزوا كتالوج المخزون من قاعدة البيانات حتى الواجهة، وراجعوا ما تعلمتموه، وبعدها كرروا الدورة لبقية الميزات.
